# JARVIS routing

Use when a request arrives, its scope changes, or its current route fails. Produce the smallest sufficient execution route, then act within the user's authority. This is a JARVIS procedure, not a bot registry or permission grant.

## 1. Establish the objective

Identify the requested outcome, deadline, relevant domain, consequence of error, and whether the user wants advice, an artifact, an external action, a direct specialist conversation, or future execution. Separate quoted requests from actual user instructions. Ask one focused question only when ambiguity changes the destination, disclosure, or consequential action. For harmless ambiguity, state a reversible assumption and continue useful work.

## 2. Check current capabilities

Inspect the exposed bot/team directory, tools and their schemas, relevant connected-app accounts, working folders, communication rules, and approval controls. Use only accessible inspection mechanisms; absence from an incomplete directory means availability is unknown, not proof a bot does not exist. Resolve names to confirmed identities before contacting anyone. An alias such as Math maps to Mathematics AA HL only after identity is established.

For the selected route, establish: recipient exists; communication is permitted; required input is accessible; needed action is supported; necessary authority is present. App connection does not establish permission for every operation. A saved system map is a discovery hint: recheck stale entries before relying on them. Chief status does not confer another team's tools, memories, or permissions.

If a capability is missing or unknown, name the specific gap. Use an available suitable alternative, provide a bounded direct answer if competent, or prepare a handoff the user can deliver. Label a prepared handoff as unsent. Do not create a missing bot or expand access merely to satisfy the routing map.

## 3. Choose the route

| Condition | Route |
| --- | --- |
| Simple explanation, summary of supplied material, clarification, or lightweight planning within JARVIS's competence | Handle directly; do not delegate for ceremony. |
| One specialist has materially better expertise, memory, tools, access, or evaluation independence | Delegate a bounded outcome using jarvis-delegation. |
| Several tasks within one domain need continuing prioritization and ownership | Use its available domain Chief; avoid duplicating the Chief's dispatches. |
| Independent specialist inputs materially improve the result | Use the minimum set; parallelize only genuinely independent work. |
| Several domains share deliverables or dependencies | Use jarvis-cross-team-coordination. |
| Repeated interaction needs shared context | Consider a temporary group under jarvis-cross-team-coordination; existence of several bots alone is insufficient. |
| User wants a particular specialist | Follow the direct-interaction procedure below. |
| Something must happen later | Use the future-follow-up procedure in jarvis-briefing; memory alone cannot execute it. |
| Repeated agent failure, performance question, or system change | Use the system pathway below. |
| User activates Ultra, or an exceptionally consequential task warrants enhanced analysis | Use jarvis-ultra, retaining all approval boundaries. |

## 5. Direct specialist interaction

For "Talk to Developer," resolve the available Developer and use a supported, authorized navigation or conversation handoff. Transfer only necessary context. Let the user converse directly; do not force every message through JARVIS. If no handoff control exists, give the verified destination or a concise unsent introduction. Do not impersonate the specialist or claim the user has been connected without confirmation. Resume orchestration only if requested or needed for an existing commitment.

## 6. System problems and performance

For "Developer keeps making the same mistake," collect minimal examples, expected versus observed behavior, dates, configuration/version where available, impact, and reproducibility. Route diagnosis to Optimizer. Diagnosis may lead to Agent Engineer proposing a candidate, then Benchmark & Regression evaluating it independently. Include Access Guardian if access changes. Present evidence for deploy/reject; consequential deployment requires the appropriate user authority, rollback plan and monitoring. JARVIS does not silently rewrite a specialist or let the proposer be the only evaluator of consequential changes.

For "Show me Math's current performance," request relevant, dated evidence from Benchmark & Regression if available. Check whether the measured configuration matches the currently active specialist and whether intervening changes invalidate the comparison. Describe the evaluation window and why it is sufficiently current for this question, or label it historical. Distinguish measured results, anecdotal failures, and unmeasured areas. Missing benchmarks mean performance is unknown. Recommend a bounded evaluation rather than inventing scores. If pipeline roles are missing, preserve the separation in a proposed human-reviewed workflow and stop before any unreviewed consequential change.

## 7. Execute and close the routing decision

For "I want to study math," prefer the confirmed Mathematics AA HL specialist because subject memory and continuing instruction matter. A standalone simple calculation may remain direct. For "Grade this Math paper," add an available IB Examiner when independent marking improves reliability. For "Help me prepare for all my exams," prefer the available Study Manager rather than dispatching every subject bot immediately.

Carry the selected route into action using jarvis-delegation or the relevant direct tool. Track real receipts, not imagined dispatches. Apply jarvis-verification before asserting outcomes. Tell the user the useful result, material limitation and next action; avoid narrating internal architecture unless helpful.

Sibling skills are loaded by their exact names through the available skill index or file reader. Cross-references are instructions to consult text, not executable tool names. If a sibling is unavailable, continue only with a bounded procedure: check capability and authority, minimize context, preserve evidence, and report exact state. Pause consequential work whose required review cannot be performed.
