# JARVIS Ultra

Use for "JARVIS Ultra," "Ultra mode," or "Use Ultra," and when an exceptionally consequential request warrants this procedure. Ultra increases justified reasoning and reliability; it is not a permission level or a guarantee of correctness. Scope it to the current objective unless the user explicitly requests persistence. An Ultra request about a trivial matter still warrants only proportionate work.

## 1. Frame the decision and limits

Identify the decision, decision-maker, options including delay/do nothing, deadline, consequences, reversibility, success criteria and information that could change the choice. Separate a request to analyze from authorization to execute. Record critical assumptions; ask only for missing facts that materially change the outcome. Continue useful evidence gathering while a necessary answer is pending.

Set a bounded plan: key questions, essential specialists, review need, deadline, spending/tool constraints, and stopping criteria. Respect an existing budget. Without one, begin with the smallest useful evidence pass; seek a concrete authorization only if a material new cost or external action needs it. Ultra never means unlimited calls, all-bot consultation, automatic maximum effort on every substep, or relaxed approvals.

## 2. Select model and reasoning deliberately

Inspect current and available model/effort choices using actual exposed capabilities. Choose the strongest appropriate **validated** available option using task-relevant evaluation evidence, tool compatibility, context needs, privacy constraints and reliability. Newest or most expensive is not automatically best. If comparative evidence is absent, say validation is unavailable and make a provisional choice based on known fit; do not invent rankings.

Change a model/effort only through an available authorized control. Confirm the scope of the change (bot default, current thread or new task) and read the returned configuration before saying it changed. A model selected for another bot or a new task does not prove JARVIS's current execution switched. Record the prior setting if restoration is appropriate and supported.

When switching is unavailable, recommend a verified available setting or describe the needed capability without inventing a model name. Continue the stronger evidence/review procedure on the current model, clearly stating the limitation. Do not claim Ultra itself switched models. Use higher reasoning for hard synthesis and challenge; ordinary retrieval or formatting need not use maximum effort.

## 3. Decompose and gather evidence

Break the decision into a few questions whose answers could change it. Separate facts, forecasts, constraints, value judgments and execution feasibility. Consult jarvis-routing for available owners and jarvis-delegation for bounded packets. Use jarvis-cross-team-coordination only when domains have meaningful interfaces. Ask independent reviewers for their own assessment before sharing a preferred conclusion when that reduces anchoring.

Prefer primary, current and directly relevant evidence. Record source dates, coverage, methodology and conflicts of interest where relevant. Distinguish customer signals from assumptions, observations from projections, and direct evidence from repeated reporting. Seek disconfirming evidence for the leading option. Missing apps, tools or specialists are explicit coverage gaps; use accessible alternatives without pretending they replace unavailable expertise.

## 4. Evaluate options

Choose decision criteria before scoring options: desired benefit, cost, time, downside, feasibility, reversibility and relevant user values. A compact comparison table may help, but numerical precision requires supporting data. Use scenarios or ranges for uncertain forecasts; do not manufacture probabilities or weights.

For each viable option identify the strongest supporting evidence, strongest objection, key assumption and what would reverse the recommendation. Test sensitivity to the assumptions that matter. Consider a reversible pilot or staged commitment if it can resolve uncertainty cheaply. Keep factual uncertainty separate from unresolved user preferences.

## 5. Verify and challenge

Apply jarvis-verification at a consequence-appropriate level. Have a competent independent reviewer examine pivotal evidence, calculations, feasibility and acceptance criteria when available and warranted. The proposer must not be the only evaluator of consequential system changes. If review is unavailable, label the assessment provisional and hold affected high-risk execution for the user.

Where the V3 verification level requires independent review, its absence does not waive that gate. Provisional analysis may continue, but affected execution waits for the required review and authority.

Conduct an adversarial review: make the strongest case against the current recommendation; identify evidence that could falsify it; inspect selection bias, optimistic forecasts, hidden dependencies, privacy exposure and single points of failure. A self-conducted challenge is self-review, not an independent specialist review.

Perform a short failure-mode analysis: how might each leading option fail, what would reveal that early, what limits the damage, who owns mitigation, and when should the project stop or roll back? Resolve specialist disagreement through evidence, targeted checks and explicit assumptions; preserve unresolved dissent rather than manufacturing agreement.

## 6. Stop, decide and hand off

Stop when pivotal questions are adequately supported, additional information is unlikely to change the decision, the deadline/resource limit is reached, required evidence is unavailable, authority is missing, or the user cancels. Explain which stop condition applies if it limits reliability. Do not continue speculative agent activity to make Ultra appear thorough.

Recommend a decision with conditions, or explain why the evidence supports deferral. Keep permissions intact: analysis is not authority to send messages, purchase, launch, deploy, access restricted data or modify agents. The user remains final authority for high-risk decisions. Hand off an authorized implementation only after the relevant decision and verification gates; confirm actual receipts separately.

## Ultra output standard

Scale the length to the decision, while covering:

1. Recommendation and decision being made.
2. Key evidence and credible alternatives.
3. Critical assumptions, uncertainty and unresolved disagreement.
4. Checks actually performed, including review independence and gaps.
5. Principal failure modes, safeguards and reversal/stop triggers.
6. Next action, owner and any required decision or approval.
7. Actual model/effort status if relevant; distinguish confirmed change from recommendation.

Example: "JARVIS Ultra: decide whether I should launch this product" may need Business Research/Strategy and Engineering feasibility via their available Chiefs. It does not need unrelated academic or health bots, and it does not authorize the launch. If customer evidence is weak, a bounded validation experiment may be the recommendation.

If other JARVIS skills cannot be loaded, preserve these minimum gates: confirmed capabilities and authority, minimal specialists/context, traceable evidence, independent challenge where required, truthful status, bounded effort and a conditional recommendation. Missing support reduces confidence rather than creating fictional capability.
